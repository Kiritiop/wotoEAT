R-1 (L): RECIPES MUST BE REAL, NOT PLAUSIBLE          [raised 2026-08-25]
════════════════════════════════════════════════════════════════════
Jerry: "Whenever you ask any LLM to generate you a dish and a recipe, it
would be different from what we actually have in our program currently. I
want it to be an actual recipe that the user could follow accurately to
cook a real meal and not just a personal project."

The problem. Every recipe is generated fresh from a prompt, so two asks
for the same dish give different ingredients, quantities and timings, and
none of them is anchored to a recipe anyone has ever cooked. The prompt
already forces REAL dish NAMES (the AUTHENTICITY block), but the method
underneath is invented each time. A 45-minute 红烧排骨 with 1 tsp of sugar
is not wrong enough to notice and not right enough to follow.

Why this is the same class of bug as the images. The image work ended at
"look at the actual photo", because a plausible-looking answer sails
through every check that does not compare it to the real thing. The recipe
equivalent is "anchor to an actual recipe", and no amount of prompt tuning
substitutes for that.

Directions, roughly cheapest first:
- Anchor to a source. TheMealDB already returns full ingredients and
  instructions for the dishes it knows, and images.py already queries it
  by name. When a dish matches, serve THAT recipe and let the AI only
  translate and scale it. Free, no key, and the meal card is already
  showing its photo. Covers maybe 300 well-known dishes.
- Widen with a real recipe corpus (Spoonacular, Edamam, or a scrape of a
  permissively licensed set). Licensing needs checking before shipping.
- Keep generation only as the fallback for dishes nothing has, and label
  it in the UI so the user knows which kind they are looking at.
- Whatever the source, pin it: a saved recipe must not silently change
  the next time it is opened.

Verification, since this is where the last three rounds went wrong: pick
20 well-known dishes, generate each, and compare ingredients and method
against a published recipe. Count how many a competent cook would call
that dish. No prompt change ships on a claim that it "looks better".

- GET THE LEGAL TEXT REVIEWED. constants/legal.ts renders a DRAFT banner on
  every document and stays that way until a lawyer sees it. Storing
  allergies and body measurements makes this non-optional.
- Supabase Auth > URL Configuration > Redirect URLs must include
  https://wotoeat.com/auth/reset-password (and
  http://localhost:8081/auth/reset-password for local testing), or password
  reset silently falls back to the Site URL and stays broken in production.
- Check whether custom SMTP is configured. Supabase's built-in sender is
  rate-limited and they say not to use it in production.
- Check whether email confirmation is required on sign-up. If it is,
  sign-up.tsx never tells the user to look in their inbox.
- A working Support URL for App Store review. Ko-fi and LinkedIn do not
  count; reviewers click it and expect a way to contact a human.
- Play Data Safety form: declare health data, and match the privacy policy
  exactly. Mismatches are a common rejection.
- Apple privacy manifest (PrivacyInfo.xcprivacy) with required-reason API
  declarations. AsyncStorage writes to UserDefaults, which is on the list.
- Check Supabase backup retention. The health profiles live there and the
  free tier retains very little.
- Turn on GitHub secret scanning, push protection, and private
  vulnerability reporting (SECURITY.md points people at it).
- Decide whether `sex` and `weight_kg` are needed at all. "Only collect
  necessary data" bites hardest on Article 9 fields, and the calorie
  estimate may not need them.

OPEN ENGINEERING DEBT
════════════════════════════════════════════════════════════════════
- A-1 (M) Sync Supabase calls inside async endpoints block the
  single-worker event loop during DB I/O (every routers/*.py db.* call).
  One slow query stalls all concurrent requests. Wrap in
  run_in_threadpool, or make those endpoints plain def so FastAPI
  threads them. It touches every router and wants load testing, not a
  blind refactor.
- A-3 (M) Dynamic zh translation scrapes an unofficial Google endpoint
  (services/translate.ts) with MyMemory fallback; either can break any
  day. Sturdier: a backend /translate endpoint on Groq with the SQLite
  cache and a rate limit, frontend falls back to passthrough.
- A-5 (M) discover.tsx (~1450 lines) and recipes.tsx (1214) are
  monoliths; extract MealSlotCard + detail modal + filter panel into
  components/. MealSlotCard is now memoized with stable callbacks from
  the parent, so it is a cleaner cut than it was.
- A-6 (note) SQLite cache/rate counters live at /tmp: wiped per deploy
  (acceptable) and per-process (fine at 1 worker; revisit if workers
  are ever added).

UI / UX PLAN
════════════════════════════════════════════════════════════════════
UI-3 (S-M) Typography ramp
    Everything is the system font. Add one display font for screen titles
    and meal names (expo-google-fonts; candidates: Fraunces, DM Serif
    Display, warm food-brand feel), keep system font for body. Define the
    ramp in useTheme fontSize tokens so it applies everywhere at once.

UI-4b (M) Shared-element transition into the detail sheet
    The rest of the motion pass shipped. This one needs the modal
    restructured, which is why it did not.

UI-5 (S) Unify toasts
    cartBanner, savedBanner, share-copied checkmarks, and ErrorBanner are
    four ad-hoc patterns. One Toast component with a queue (success /
    error / info), used everywhere. Removes duplicated code and makes
    feedback consistent.

UI-6 (S) Dark mode decision
    useTheme already follows the system scheme, so users with dark-mode
    phones are ALREADY seeing the dark palette, and it has never been
    audited screen by screen. Either pin the app to light until there is
    time to audit, or do the audit (contrast, borders, images on dark).
    Right now it is an unreviewed surface users can land on.

UI-7 (S) Landing and brand assets
    - Transparent-background logo export (current PNG has baked-in cream)
    - Regenerate app icon / adaptive icon / favicon / splash from it.
      All six are currently the same byte-identical 298KB PNG, which makes
      the favicon roughly 300x bigger than it needs to be.
    - Subtle entrance animation on the landing logo

UI-8 (M) Onboarding polish
    One question per screen with progress dots, warmer copy, visible skip.
    First-run experience is the highest-leverage screen for a new user.

UI-9 (S) Installable PWA
    public/ has og.png, robots.txt and sitemap.xml but no manifest.json.
    Add one (name, icons, standalone display, theme colour) so phone-web
    users can add wotoEAT to their home screen and lose the browser
    chrome. Cheap store-app feel without app stores.

UI-10 (S-M) Accessibility sweep, part two
    Icon-only controls are labelled and images have alt text. Still open:
    contrast-check the cream/green pairs against WCAG AA (4.5:1 body,
    3:1 large) in BOTH themes, starting with c.textMuted and
    c.textPlaceholder on c.surface and c.bg; confirm 44pt targets on the
    small icon buttons (share/trash on Shopping, the steppers); Dynamic
    Type spot check; a keyboard-only web pass (tab order, visible focus
    rings, Escape closing modals, skip-to-content), none of which RN Web
    gives for free; pull-to-refresh on Today/Recipes/Pantry.

UI-11 (decision) Today-card imagery
    Guardrail says no images on Today cards (perf). Middle ground worth
    considering: show a thumbnail ONLY when the image is already in cache
    from a previously opened detail sheet (zero new fetches), or add
    slot-coloured abstract accents instead. Decide, then document.

UI-12 (S) Localise the native header titles
    app/_layout.tsx hardcodes "Meal Detail", "Add Recipe", "Scan Receipt",
    "Shared Recipe" and "Back" in English, in an otherwise bilingual app.

PRODUCT FEATURES
════════════════════════════════════════════════════════════════════
P-2 (M) Cook mode
    Full-screen step-by-step view from any recipe: one step per screen,
    big text readable from a counter, swipe to advance, keep-awake, and
    an inline timer when a step mentions minutes. This is the moment the
    user is actually cooking; the app currently abandons them there.

P-3 (L) Household sharing (the flagship candidate)
    Share pantry + shopping list between two accounts (invite by email).
    Built for the actual primary use case: two people, one kitchen. One
    person confirms meals, the other sees the shopping list update.
    Needs a households table, membership, and scoping pantry/shopping
    queries by household instead of user. Biggest feature on this list,
    and the one that makes the app genuinely shared.

P-4 (M) Recipe import from photo
    The vision pipeline exists (receipt scanning). Point it at cookbook
    pages / handwritten cards / restaurant menus: photo to parsed recipe
    to saved. Reuses transcribe + normalize pattern wholesale.

P-5 (S) Cook again from history
    History shows past meals but offers no one-tap path to re-cook:
    add a button that regenerates the full recipe and jumps to it.

P-6 (M) Today's nutrition summary
    Confirmed meals already carry macros; sum them on Today against the
    profile calorie/protein goals (small progress ring under the header).
    Makes the health-profile data visibly useful, currently it only
    shapes generation invisibly.

P-7 (S-M) Weekly digest on History
    "This week: 9 meals, 5 cuisines, most cooked: stir-fry". Cheap
    aggregation over meal_history, gives the write-only table a purpose
    and users a reason to return.

P-8 (M-L) Daily dinner reminder (notifications)
    "What's for dinner?" push at a user-chosen hour, deep-links to Today.
    Needs expo-notifications + EAS native build (no web equivalent).
    Retention driver, but only worth it once native builds ship.

P-9 (M) Store-readiness leftovers
    Account deletion, the privacy policy URL and the legal pages shipped.
    Still missing: data export (GDPR portability, the other half of the
    erasure right), and Apple / Google sign-in, which Apple requires as an
    option wherever a third-party social login is offered. There is no
    social login today, so that one is conditional.

P-10 (S) Servings preference has no way to change it
    The store's `servings` is read on every generate but `setServings` has
    no caller, so it is permanently 1. Either wire a control into Profile
    or delete the field and the preference it implies.

════════════════════════════════════════════════════════════════════
ENGINEERING / INFRA
════════════════════════════════════════════════════════════════════
E-1 (S-M) Error monitoring  ** highest-value open item **
    No crash or error visibility today beyond Railway logs. Nothing
    aggregates client crashes or backend 500s, which is why the Aug 17
    outage was reported by a user. Sentry on both halves (sentry-expo,
    sentry-sdk[fastapi]) with the DSNs in env vars. Do this before
    inviting more users than friends.

E-2 (M) Privacy-light usage analytics
    Feature-level counters only (generated, confirmed, cooked, scanned,
    shared), no personal data. This is what turns future debates like
    Phase 3 ("will anyone use it?") into lookups instead of guesses.
    NOTE: the Cookies document currently states the app has no analytics
    of any kind. Adding this means updating that document too.

E-3 (M) Staging environment
    Push-to-main deploys production with no intermediate step. A staging
    branch with its own Railway service + Vercel preview and a promote
    step would make risky changes safe. Alternative smaller step: turn on
    branch protection and work through PRs.

E-4 (S) Groq model fallback chain  ** an outage already happened **
    _create_with_retry handles 429s, but a model deprecation or outage
    is a hard 503. Env-driven ordered fallback list (text + vision) in
    ai/claude.py; log when running on fallback. In Aug 2026 Groq removed
    both models at once and took every AI feature down; a fallback list
    would have degraded instead of dying. The vision side has no real
    fallback today: qwen3.6 is the only image-input model Groq offers, so
    a second provider (AWS Textract) is the honest answer there. Pair
    with E-1 so the next one pages us instead of a user.

E-6 (S) Dependency hygiene
    Dependabot now opens grouped monthly PRs for npm, pip and actions.
    Still manual: actually reviewing and merging them, and Expo SDK
    upgrades, which Dependabot cannot do safely on its own.

E-7 (S) SEO loose ends
    The homepage now exports real content, one h1, JSON-LD and a
    canonical. Still open, in rough value order:
    - Verify the site in Google Search Console and submit
      https://wotoeat.com/sitemap.xml. Nothing gets indexed quickly
      without it, and no code change substitutes.
    - /auth/* and the app tabs still export an empty first <title> and
      are crawlable. They should carry robots noindex rather than
      titles; they are not landing pages.
    - vercel.json's catch-all rewrite serves +not-found.html with a 200
      for any unknown path, which reads to Google as a soft 404. A
      custom +not-found route with a noindex tag would fix it.
    - /what-to-eat has no internal link pointing at it; it is reachable
      only through the sitemap. Fine for now, worth a link from the
      landing page if it starts ranking.
    - No backlinks anywhere. This is the actual ranking ceiling, and it
      is a promotion problem, not a code problem. As of 2026-09-22 the
      homepage is the ONLY indexed page, and the bare query "wotoeat"
      is spell-corrected to "weartoeat" and does not reach the site.
    - The logo PNG's baked-in cream fill shows as a faint square on the
      1200x630 og.png. A transparent export fixes both that and the
      landing hero.

DEFERRED / STANDING DECISIONS (do not rebuild blindly)
════════════════════════════════════════════════════════════════════
- Pantry-loop Phase 3 (server-side meal_feedback): deferred as mostly
  dead code; revisit triggers in design/pantry-loop.md Phase 3 outcome.
- Pantry stays name-only (no quantities): foundational decision, see
  design/pantry-loop.md.
- No gradients, no emojis in UI: product rules, documented in CLAUDE.md.
- seenMeals/no-repeat and same-day stream persistence are features, not
  bugs (CLAUDE.md).
- No stock-photo search. The Pexels stage and its vision gate were removed
  2026-08-25 after a chain of misses that ended in a supply problem no
  matching logic could solve; the cascade is TheMealDB, then generate.
  Full reasoning in CLAUDE.md's Image Search section.
- No Content-Security-Policy header. The Metro web bundle needs
  unsafe-inline and unsafe-eval, so a shipped CSP would permit exactly
  what a CSP exists to stop. Revisit if the bundle stops needing them.
- No Google "preferred sources" badge. It feeds Top Stories and
  Discover, Google's own docs scope it to news publishers, and the
  widget is a third-party script on every page load, which would end
  the app's no-tracking position and its no-cookie-banner argument.
- Not scraping 下厨房. Those photos belong to the users who uploaded them,
  下厨房 holds a licence it cannot pass on, and hot-linking their CDN from
  a public app is both infringement and trivially blockable.
