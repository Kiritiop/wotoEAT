R-1 (L): RECIPES MUST BE REAL, NOT PLAUSIBLE          [raised 2026-08-25]
════════════════════════════════════════════════════════════════════
Jerry: "Whenever you ask any LLM to generate you a dish and a recipe, it
would be different from what we actually have in our program currently. I
want it to be an actual recipe that the user could follow accurately to
cook a real meal and not just a personal project."

The problem. Every recipe is generated fresh from a prompt, so two asks
for the same dish give different ingredients, quantities and timings, and
none of them is anchored to a recipe anyone has ever cooked. The prompt
already forces REAL dish NAMES (the AUTHENTICITY block), but the method
underneath is invented each time. A 45-minute 红烧排骨 with 1 tsp of sugar
is not wrong enough to notice and not right enough to follow.

Why this is the same class of bug as the images. We spent this whole
session learning that a plausible-looking answer sails through every
check that does not compare it to the real thing. The image fix ended at
"look at the actual photo". The recipe equivalent is "anchor to an actual
recipe", and no amount of prompt tuning substitutes for that.

Directions, roughly cheapest first:
- Anchor to a source. TheMealDB already returns full ingredients and
  instructions for the dishes it knows, and images.py already queries it
  by name. When a dish matches, serve THAT recipe and let the AI only
  translate and scale it. Free, no key, and the meal card is already
  showing its photo. Covers maybe 300 well-known dishes.
- Widen with a real recipe corpus (Spoonacular, Edamam, or a scrape of a
  permissively licensed set). Licensing needs checking before shipping.
- Keep generation only as the fallback for dishes nothing has, and label
  it in the UI so the user knows which kind they are looking at.
- Whatever the source, pin it: a saved recipe must not silently change
  the next time it is opened.

Verification, since this is where the last three rounds went wrong: pick
20 well-known dishes, generate each, and compare ingredients and method
against a published recipe. Count how many a competent cook would call
that dish. No prompt change ships on a claim that it "looks better".

SHIPPED 2026-08-25: recipe image matching + guest mode
════════════════════════════════════════════════════════════════════
Recipe hero images were "never right, frequently something completely
random". Not a generation problem: /images/search matches a dish name to
an existing stock photo, and both rungs of the cascade took whatever came
back first.
  - TheMealDB search.php?s= is a substring LIKE over meal titles and the
    code used meals[0] unverified. Confirmed against the live API:
    s=Beef Stew -> "Lemongrass beef stew with noodles" (a Vietnamese
    noodle bowl); s=Chicken Curry -> "Katsu Chicken curry"; s=Chicken ->
    30 hits, first is "Chicken Handi".
  - Pexels: per_page=1 on a loose multi-word query, used unconditionally.
  - Wrong URLs were cached 7 days, so one bad match served every user for
    a week.
Fixed by verifying every candidate: MealDB titles must be a word-subset
of our dish name (exact match wins; one-word titles must match exactly);
Pexels returns 15 and each is scored against its own alt text with a 0.5
floor plus a narrowed retry; below the floor we return {url: null} and
show the placeholder. Cache key prefixed img:v2: so the poisoned week
clears on deploy - bump _CACHE_VERSION on any future matching change.
The root cause was that AI dish names are marketing copy, so the
generator now emits image_query ("Coq au Vin" -> "braised chicken red
wine") which the app passes as ?hint=; MealDB still searches the real
name. Locked by tests/test_image_match.py (17) and
tests/test_image_endpoint.py (16), both offline and in CI.

Guest mode: "Look around first" on the landing page lets people try the
app with no account. The backend already allowed the core loop
anonymously; only the frontend router blocked it. One API change:
/recipes/generate was require_user_id and is the "show me the steps" call
behind every meal card, so it dead-ended guests - it writes nothing, and
the user id was only ever the rate-limit key, so it now falls back to IP
like /meals/generate does. Pantry, saved recipes and history swap to
GuestGate; profile stays usable (it is local state that feeds generation)
with the server save skipped. Sign-up runs a server-aware handoff: empty
account -> push local up, existing account -> adopt the server's copy.
Locked by tests/test_guest_endpoints.py (15) and a Playwright pass over
the production web build (27 checks).
Caught during that browser pass: gating Pantry orphaned the shopping
list, because the shopping tab is href:null and only reachable from the
Pantry header cart. GuestGate now takes a headerRight slot and Pantry
passes its cart through.
Follow-up the same day: Beef Bulgogi and Beef Bibimbap came back with
visually identical heroes. Not a scoring miss - Pexels 5774004 and 5774005
are consecutive frames of one Luis Becerra shoot whose alt text names
bibimbap AND bulgogi beef, so both scored ~1.0 for both dishes and each
dish took its top scorer. Correct photos, wrong pair. Scoring cannot fix
that, so a chosen photo (and its shoot, via photographer_id) is now
claimed for its dish in the TTL cache; a later dish skips claimed ones,
ties break on a stable sha1(dish|photo_id) shuffle, and if everything is
claimed it falls back to the best scorer rather than showing nothing.
per_page raised 15 -> 30 so an unclaimed alternative usually exists.
Locked by tests/test_image_distinct.py (8), built from the real payloads.

Second follow-up: 红烧排骨 (braised pork RIBS) was shown a braised pork
BELLY photo. Scoring counted every query word the same, so `braised` and
`pork` matched and `ribs`, the only word that makes it that dish, counted
for no more than either: 0.67, accepted. Same class of miss was live for
chicken tikka masala, which was being served a photo of chicken biryani.
Fixed by weighting: cooking method, staple, vessel, broad protein and
cuisine count 1, anything that actually identifies a dish counts 4. Pork
belly now scores 0.33 and biryani 0.38, both rejected, while the right
photo scores 1.0 and outranks the near misses. A query with no
distinctive word behaves exactly as before.
Found while fixing it: the narrow-and-retry step scored candidates
against its own shortened term list, so retrying "braised pork ribs" as
"braised pork" re-accepted the very photo the first pass rejected. Query
terms and scoring terms are now separate arguments; a retry broadens what
we ASK Pexels (now "ribs food", the distinctive words only) and never
what we ACCEPT.
Also confirmed: _normalize keeps [a-z0-9], so a Chinese dish name yields
no tokens at all and returns null. image_query being English is not a
nicety for zh users, it is their only search signal. The prompt's old
examples actively taught the model to throw the identifying word away
("Bibimbap" -> "korean rice bowl vegetables"); it now must keep the cut,
form or dish name and is forbidden from swapping it for a broader word.
Locked by tests/test_image_specificity.py (8) and 9 more checks in
test_image_match.py.

Third follow-up, and the end of the text-matching road: "Red Braised Pork
Ribs" was shown a rack of ribs on an American barbecue. The photo shares
every word that matters (pork, ribs) and differs only by cooking method,
which is true of thousands of dishes and so cannot be weighted heavily
without rejecting everything. It scores 0.83 even WITH the weighting fix.
Alt text is one line written by whoever uploaded the photo; no amount of
tuning turns it into a description of what the picture looks like.
So the pipeline now looks at the image. Text scoring picks the shortlist,
the top 3 go to the vision model concurrently, and only a photo it agrees
shows the dish is served. It is a veto and never an approval: a broken or
unreachable model returns unverified and the text choice stands, since a
flaky vision call must not strip every recipe of its image. All three
rejected means no hero, with no fallback to unchecked candidates. A
verified MealDB name match skips the gate, being a photo of that exact
recipe. IMAGE_VISION_CHECK=0 turns it off.
Locked by tests/test_image_vision.py (13, model stubbed). The model's
JUDGMENT is not testable offline: run scripts/check_dish_photo.py with a
real key to see it working on the dishes that have gone wrong so far.

First live run of the vision gate (scripts/check_dish_photo.py, real key):
3 of 5 stock lookups were still wrong and the gate approved all three.
Colombian rib roast for a Chinese red braise, PANEER tikka masala for
CHICKEN tikka masala, a bibimbap bowl for bulgogi. Every one of those was
listed in the prompt as a reject condition. The lesson: asking a 27B
model "would a person accept this photo" with a confidence field gets a
confident yes every time. A lenient binary is not a filter.
Rewritten as a discriminative rating. The model describes the photo
first, then answers same_main_ingredient and same_style as separate
booleans, then gives a 0-10 fit with explicit anchors. Usable requires
both booleans and fit >= 6. Fit is now the primary ranking key, so
candidates compete against each other rather than each being waved
through alone.
Same run exposed a second thing: "Red Braised Pork Ribs" and "红烧排骨"
are the same dish under two names, and the claim system pushed the second
off the good photo onto a worse one. Distinctness now only breaks ties, a
dish may reuse a claimed photo when the best free alternative is worse by
more than _FIT_TOLERANCE (2 bands).
Also seeded _no_reasoning_effort with qwen: the first image check after
every deploy was burning three concurrent 400s learning it again.
STILL UNVERIFIED: whether the rewritten prompt actually rejects those
three. Re-run scripts/check_dish_photo.py (fresh cache per run now) and
read the fit lines.

CORRECTION to the entry above: the gate was never rubber-stamping. It
was never running. Second live run showed every candidate coming back
"fit 0/10, photo shows 'unverified'", which is the sentinel for the call
having thrown. The vision model reasons before answering and Groq bills
that as completion tokens; max_tokens was set to 400, about the size of
the <think> block alone. Every reply truncated before its JSON, every
parse raised, and the fail-open path returned approved every time. Two
releases shipped a no-op whose own logs read "kept".
The previous entry's conclusion, that a 27B model waved through Colombian
ribs and paneer, was wrong: the model never answered. The prompt rewrite
it triggered is still an improvement and stays, but it fixed something
that was not the problem.
Fixed: _VISION_CHECK_MAX_TOKENS = 4000, truncation detected by name,
every failure logged at WARNING with the raw reply, and the router says
plainly when a photo went out unchecked. verify_dish_photo returns
shows == UNVERIFIED so callers can tell "model said fine" from "model
never answered". scripts/check_dish_photo.py --debug prints raw replies.
The real lesson is not the token budget. A check that fails open and
fails silently is indistinguishable from one that works, and 178 passing
assertions did not notice because they all stubbed the model with
well-formed replies. tests/test_vision_contract.py now feeds it the
shapes a reasoning model actually produces.
STILL UNVERIFIED: whether the model, once it can actually reply, rejects
the Colombian ribs and the paneer.

Third live run, gate finally executing, and it works. Red Braised Pork
Ribs 10/10 on an actual red braise, with the Colombian rib roast rejected
at 4/10 ("Western presentation, roasted new potatoes") and a foil-wrapped
rack with fries at 0/10. Beef Bulgogi 8/10 on sliced beef, correctly
rejecting BOTH bibimbap bowls at 4/10 via the rice-bowl rule. 红烧排骨 got
the same photo as its English name, so the fit-tolerance change works.
Three things that run exposed:
1. 4000 tokens still truncated one reply. The model rambles hardest on
   the ambiguous photos the check exists for; replies ran 1.8k-13.7k
   chars. Now 8000, plus a prompt line telling it not to re-examine.
2. Both photos Pexels titles "paneer tikka masala" went to the vision
   model, which read one as chicken and gave it 10/10. Caption and pixels
   disagree about the protein and one of them is wrong. _contradicts now
   drops a candidate whose caption names a different main ingredient
   before spending a vision call, so the shortlist goes to photos where
   both signals agree (20446401, chicken, also rated 10/10).
3. Cost is real now: 3 candidates x ~800-3400 output tokens per novel
   dish, roughly 3 cents worst case. Cached 7 days, capped 60/hr/IP. The
   brevity instruction and the contradiction guard both cut it. Dials are
   _VISION_CANDIDATES and IMAGE_VISION_CHECK.

Fourth round, on Jerry's report that 红烧排骨 came back as a Sichuan
chilli-oil braise and that the check added 10-15s of wait:
- Prewarm. /meals/generate and /meals/swap now start resolving photos for
  the dishes they just produced, fire-and-forget, so the vetting overlaps
  with the user reading the card instead of sitting between the tap and
  the hero. /images/search is normally a cache hit now.
- The vision check reads the recipe's own description. It was judging
  against a generic idea of the name, which is how a chilli-oil braise
  scored 10/10 for a recipe whose text says 色泽红亮，酱香浓郁.
- Pexels locale. The API indexes contributor keywords per language, so a
  Chinese dish is now searched in zh-CN, Korean in ko-KR, and so on.
- Generated images as the LAST rung, using the Gemini key already sitting
  unused in .env, stored in a public Supabase bucket. Only fires when no
  real photo survives vetting, because a made-up picture must never
  displace a photograph of real food.
Note the coupling: generation only helps when the gate REJECTS
everything. A photo the gate wrongly accepts is never replaced, so the
description change is what makes the generation fallback reachable.

Asked about scraping 下厨房: not doing it. Those photos belong to the
users who uploaded them, 下厨房 holds a licence to display them and cannot
pass it on, and hot-linking their CDN from a public app is both
infringement and trivially blockable. It stays a good reference for what
a dish should LOOK like, which is how it was used here.
Sources still worth trying, both blocked from the dev sandbox so
untested: Wikimedia Commons (genuinely free-licensed, real regional
photos, some need CC BY-SA attribution) and Openverse (aggregates
Flickr/Commons, keyless API, returned 403 from here).

Open follow-ups: Pexels attribution is still not shown (their terms ask
for it); guests are invisible server-side, so there is no funnel data.
Matching is now strict enough that some dishes will legitimately get no
photo. The hero is conditional so a blank reads fine; if too many come
back empty the levers are _DISTINCT_WEIGHT (4), _PEXELS_FLOOR (0.5) or
_VISION_CANDIDATES (3), not the retry.
Cost and latency are the thing to watch: a novel dish now costs up to 3
vision calls and a few seconds. Cached 7 days per dish, capped at 60/hr
per IP, and the whole gate is one env var away from off.

INCIDENT 2026-08-17: Groq decommissioned both models (RESOLVED)
════════════════════════════════════════════════════════════════════
Every AI endpoint returned 503. Cause was not capacity: Groq removed
llama-3.3-70b-versatile AND meta-llama/llama-4-scout-17b-16e-instruct
from the account. A removed model 404s as model_not_found -> APIStatusError
-> GroqTransientError -> the routers' blanket 503. Meal generation, swap,
recipe generate/parse, shopping generation and receipt scanning were all
down; only the non-AI paths still worked.
Fixed by: text default -> openai/gpt-oss-120b, vision default ->
qwen/qwen3.6-27b (the only image-input model Groq still offers), plus
_clean_json now strips <think> preambles (both new models are reasoning
models; qwen always emits one, which broke every JSON parse).
Verified live against all six AI paths + the live receipt test.
Second-order problem found while measuring: gpt-oss bills reasoning as
completion tokens, so at Groq's default effort an elaborate recipe
(cassoulet, 6 servings) spent ~2500 of its 4500 budget thinking and
truncated mid-JSON into a 422. Raising the budget did not help, it just
expanded to fill it. Fixed properly with reasoning_effort=low
(GROQ_REASONING_EFFORT), which dropped worst-case budget use from 98% to
42% and roughly halved cost and latency. Models that reject the param
(qwen, compound, allam) self-heal at runtime so a model swap still works.
Measured after: meal generate 1.9s avg uncached, recipe generate 4.0s,
text flows 0.4-0.6x the old cost. Receipt scan is ~4x the old cost
(qwen output is $3/M vs Scout's $0.34/M) but it is capped at 10/hr/user.
Follow-ups this exposed:
- E-4 (Groq model fallback chain) is no longer hypothetical. Promote it.
- Nothing alerts on this. Every AI feature was dead until a user
  reported it. Pairs with E-1 (error monitoring).
- Check Railway does NOT pin GROQ_TEXT_MODEL / GROQ_VISION_MODEL to the
  dead models; an env override there beats the code default.
