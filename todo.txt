SHIPPED 2026-08-25: recipe image matching + guest mode
════════════════════════════════════════════════════════════════════
Recipe hero images were "never right, frequently something completely
random". Not a generation problem: /images/search matches a dish name to
an existing stock photo, and both rungs of the cascade took whatever came
back first.
  - TheMealDB search.php?s= is a substring LIKE over meal titles and the
    code used meals[0] unverified. Confirmed against the live API:
    s=Beef Stew -> "Lemongrass beef stew with noodles" (a Vietnamese
    noodle bowl); s=Chicken Curry -> "Katsu Chicken curry"; s=Chicken ->
    30 hits, first is "Chicken Handi".
  - Pexels: per_page=1 on a loose multi-word query, used unconditionally.
  - Wrong URLs were cached 7 days, so one bad match served every user for
    a week.
Fixed by verifying every candidate: MealDB titles must be a word-subset
of our dish name (exact match wins; one-word titles must match exactly);
Pexels returns 15 and each is scored against its own alt text with a 0.5
floor plus a narrowed retry; below the floor we return {url: null} and
show the placeholder. Cache key prefixed img:v2: so the poisoned week
clears on deploy - bump _CACHE_VERSION on any future matching change.
The root cause was that AI dish names are marketing copy, so the
generator now emits image_query ("Coq au Vin" -> "braised chicken red
wine") which the app passes as ?hint=; MealDB still searches the real
name. Locked by tests/test_image_match.py (17) and
tests/test_image_endpoint.py (16), both offline and in CI.

Guest mode: "Look around first" on the landing page lets people try the
app with no account. The backend already allowed the core loop
anonymously; only the frontend router blocked it. One API change:
/recipes/generate was require_user_id and is the "show me the steps" call
behind every meal card, so it dead-ended guests - it writes nothing, and
the user id was only ever the rate-limit key, so it now falls back to IP
like /meals/generate does. Pantry, saved recipes and history swap to
GuestGate; profile stays usable (it is local state that feeds generation)
with the server save skipped. Sign-up runs a server-aware handoff: empty
account -> push local up, existing account -> adopt the server's copy.
Locked by tests/test_guest_endpoints.py (15) and a Playwright pass over
the production web build (27 checks).
Caught during that browser pass: gating Pantry orphaned the shopping
list, because the shopping tab is href:null and only reachable from the
Pantry header cart. GuestGate now takes a headerRight slot and Pantry
passes its cart through.
Follow-up the same day: Beef Bulgogi and Beef Bibimbap came back with
visually identical heroes. Not a scoring miss - Pexels 5774004 and 5774005
are consecutive frames of one Luis Becerra shoot whose alt text names
bibimbap AND bulgogi beef, so both scored ~1.0 for both dishes and each
dish took its top scorer. Correct photos, wrong pair. Scoring cannot fix
that, so a chosen photo (and its shoot, via photographer_id) is now
claimed for its dish in the TTL cache; a later dish skips claimed ones,
ties break on a stable sha1(dish|photo_id) shuffle, and if everything is
claimed it falls back to the best scorer rather than showing nothing.
per_page raised 15 -> 30 so an unclaimed alternative usually exists.
Locked by tests/test_image_distinct.py (8), built from the real payloads.

Open follow-ups: Pexels attribution is still not shown (their terms ask
for it); guests are invisible server-side, so there is no funnel data.

INCIDENT 2026-08-17: Groq decommissioned both models (RESOLVED)
════════════════════════════════════════════════════════════════════
Every AI endpoint returned 503. Cause was not capacity: Groq removed
llama-3.3-70b-versatile AND meta-llama/llama-4-scout-17b-16e-instruct
from the account. A removed model 404s as model_not_found -> APIStatusError
-> GroqTransientError -> the routers' blanket 503. Meal generation, swap,
recipe generate/parse, shopping generation and receipt scanning were all
down; only the non-AI paths still worked.
Fixed by: text default -> openai/gpt-oss-120b, vision default ->
qwen/qwen3.6-27b (the only image-input model Groq still offers), plus
_clean_json now strips <think> preambles (both new models are reasoning
models; qwen always emits one, which broke every JSON parse).
Verified live against all six AI paths + the live receipt test.
Second-order problem found while measuring: gpt-oss bills reasoning as
completion tokens, so at Groq's default effort an elaborate recipe
(cassoulet, 6 servings) spent ~2500 of its 4500 budget thinking and
truncated mid-JSON into a 422. Raising the budget did not help, it just
expanded to fill it. Fixed properly with reasoning_effort=low
(GROQ_REASONING_EFFORT), which dropped worst-case budget use from 98% to
42% and roughly halved cost and latency. Models that reject the param
(qwen, compound, allam) self-heal at runtime so a model swap still works.
Measured after: meal generate 1.9s avg uncached, recipe generate 4.0s,
text flows 0.4-0.6x the old cost. Receipt scan is ~4x the old cost
(qwen output is $3/M vs Scout's $0.34/M) but it is capped at 10/hr/user.
Follow-ups this exposed:
- E-4 (Groq model fallback chain) is no longer hypothetical. Promote it.
- Nothing alerts on this. Every AI feature was dead until a user
  reported it. Pairs with E-1 (error monitoring).
- Check Railway does NOT pin GROQ_TEXT_MODEL / GROQ_VISION_MODEL to the
  dead models; an env override there beats the code default.

OPEN ENGINEERING DEBT (from the 2026-07-08 review + audit)
════════════════════════════════════════════════════════════════════
FIX-1..FIX-10, A-2 and A-4 all shipped 2026-08-18 and have been removed
from this file; see git history for what they were. What is left is the
work that needs a real design decision rather than a patch:

- A-1 (M) Sync Supabase calls inside async endpoints block the
  single-worker event loop during DB I/O (every routers/*.py db.* call).
  One slow query stalls all concurrent requests. Wrap in
  run_in_threadpool, or make those endpoints plain def so FastAPI
  threads them. Deliberately not done in the 08-18 sweep: it touches
  every router and wants load testing, not a blind refactor.
- A-3 (M) Dynamic zh translation scrapes an unofficial Google endpoint
  (services/translate.ts) with MyMemory fallback; either can break any
  day. Sturdier: a backend /translate endpoint on Groq with the SQLite
  cache and a rate limit, frontend falls back to passthrough.
- A-5 (M) discover.tsx (~1450 lines) and recipes.tsx (1214) are
  monoliths; extract MealSlotCard + detail modal + filter panel into
  components/. MealSlotCard is now memoized with stable callbacks from
  the parent, so it is a cleaner cut than it was.
- A-6 (note) SQLite cache/rate counters live at /tmp: wiped per deploy
  (acceptable) and per-process (fine at 1 worker; revisit if workers
  are ever added).

UI / UX PLAN
════════════════════════════════════════════════════════════════════
UI-3 (S-M) Typography ramp
    Everything is the system font. Add one display font for screen titles
    and meal names (expo-google-fonts; candidates: Fraunces, DM Serif
    Display, warm food-brand feel), keep system font for body. Define the
    ramp in useTheme fontSize tokens so it applies everywhere at once.

UI-4 shipped 2026-08-18: FadeSlideIn on appended/swapped meal cards,
    Collapsible on the filter panel (animates both ways now), press-scale
    on the shared Button, spring pop on the shopping checkbox. Not done:
    a shared-element transition into the detail sheet, which would need
    the modal restructured.

UI-5 (S) Unify toasts
    cartBanner, savedBanner, share-copied checkmarks, and ErrorBanner are
    four ad-hoc patterns. One Toast component with a queue (success /
    error / info), used everywhere. Removes duplicated code and makes
    feedback consistent.

UI-6 (S) Dark mode decision
    useTheme already follows the system scheme, so users with dark-mode
    phones are ALREADY seeing the dark palette, and it has never been
    audited screen by screen. Either pin the app to light until there is
    time to audit, or do the audit (contrast, borders, images on dark).
    Right now it is an unreviewed surface users can land on.

UI-7 (S) Landing and brand assets
    - Transparent-background logo export (current PNG has baked-in cream)
    - Regenerate app icon / adaptive icon / favicon / splash from it
    - Subtle entrance animation on the landing logo

UI-8 (M) Onboarding polish
    One question per screen with progress dots, warmer copy, visible skip.
    First-run experience is the highest-leverage screen for a new user.

UI-9 (S) Installable PWA
    public/ has only og.png. Add manifest.json (name, icons, standalone
    display, theme colour) so phone-web users can add wotoEAT to their
    home screen and lose the browser chrome. Cheap store-app feel without
    app stores.

UI-10 (S-M) Accessibility and consistency sweep
    Contrast check the cream/green pairs, confirm 44pt targets on the
    small icon buttons (share/trash on Shopping, steppers), Dynamic Type
    spot check, pull-to-refresh on Today/Recipes/Pantry for consistency.

UI-11 (decision) Today-card imagery
    Guardrail says no images on Today cards (perf). Middle ground worth
    considering: show a thumbnail ONLY when the image is already in cache
    from a previously opened detail sheet (zero new fetches), or add
    slot-coloured abstract accents instead. Decide, then document.

PRODUCT FEATURES
════════════════════════════════════════════════════════════════════
P-2 (M) Cook mode
    Full-screen step-by-step view from any recipe: one step per screen,
    big text readable from a counter, swipe to advance, keep-awake, and
    an inline timer when a step mentions minutes. This is the moment the
    user is actually cooking; the app currently abandons them there.

P-3 (L) Household sharing (the flagship candidate)
    Share pantry + shopping list between two accounts (invite by email).
    Built for the actual primary use case: two people, one kitchen. One
    person confirms meals, the other sees the shopping list update.
    Needs a households table, membership, and scoping pantry/shopping
    queries by household instead of user. Biggest feature on this list,
    and the one that makes the app genuinely shared.

P-4 (M) Recipe import from photo
    The vision pipeline exists (receipt scanning). Point it at cookbook
    pages / handwritten cards / restaurant menus: photo to parsed recipe
    to saved. Reuses transcribe + normalize pattern wholesale.

P-5 (S) Cook again from history
    History shows past meals but offers no one-tap path to re-cook:
    add a button that regenerates the full recipe and jumps to it.

P-6 (M) Today's nutrition summary
    Confirmed meals already carry macros; sum them on Today against the
    profile calorie/protein goals (small progress ring under the header).
    Makes the health-profile data visibly useful, currently it only
    shapes generation invisibly.

P-7 (S-M) Weekly digest on History
    "This week: 9 meals, 5 cuisines, most cooked: stir-fry". Cheap
    aggregation over meal_history, gives the write-only table a purpose
    and users a reason to return.

P-8 (M-L) Daily dinner reminder (notifications)
    "What's for dinner?" push at a user-chosen hour, deep-links to Today.
    Needs expo-notifications + EAS native build (no web equivalent).
    Retention driver, but only worth it once native builds ship.

P-9 (M) Store-readiness pack (only when app-store launch is real)
    Account deletion in Profile (App Store hard requirement), data
    export, Apple/Google sign-in, privacy policy URL.

ENGINEERING / INFRA
════════════════════════════════════════════════════════════════════
E-1 (S-M) Error monitoring
    No crash/error visibility today beyond Railway logs. Sentry on both
    halves (sentry-expo, sentry-sdk[fastapi]) with the DSNs in env vars.
    Do this before inviting more users than friends.

E-2 (M) Privacy-light usage analytics
    Feature-level counters only (generated, confirmed, cooked, scanned,
    shared), no personal data. This is what turns future debates like
    Phase 3 ("will anyone use it?") into lookups instead of guesses.

E-3 (M) Staging environment
    Push-to-main deploys production with no intermediate step. A staging
    branch with its own Railway service + Vercel preview and a promote
    step would make risky changes safe. Alternative smaller step: turn on
    branch protection and work through PRs.

E-4 (S) Groq model fallback chain  ** PROMOTED: this outage happened **
    _create_with_retry handles 429s, but a model deprecation or outage
    is a hard 503. Env-driven ordered fallback list (text + vision) in
    ai/claude.py; log when running on fallback.
    2026-08-17: Groq removed both models at once and took every AI
    feature down (see INCIDENT above). A fallback list would have
    degraded instead of dying. Note the vision side has no real
    fallback today: qwen3.6 is the only image-input model Groq offers,
    so a second vision provider (AWS Textract) is the honest answer
    there. Pair with E-1 so the next one pages us instead of a user.

E-5 (S) Schema hygiene
    Drop the dead user_preferences and daily_plans tables from schema.sql
    (zero code references, documented as dead) so new environments stop
    creating them.

E-6 (S) Dependency hygiene
    Monthly: npm audit / pip list --outdated pass, Expo SDK upgrades on
    their cadence. Put a reminder in the check skill or a scheduled task.
